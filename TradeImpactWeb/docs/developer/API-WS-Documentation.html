1) Autenticazione

Endpoint per login/logout e controllo sessione. Il login stabilisce (in background) le connessioni SDP verso gli Access Point e restituisce un token di sessione che deve essere usato per le richieste successive.

POST /api/auth/login

MetodoPOST
Path/api/auth/login
Body (JSON) 
{
  "username": "dev",
  "password": "dev",
  "ipspHost": "ipsp.example.com",
  "ipspPort": 8800,
  "useSsl": true
}
Response (200) 
{
  "success": true,
  "token": "",
  "username": "dev",
  "connected": true
}

POST /api/auth/logout

Invalidate la sessione. Fornisce header `Authorization` con il token.

Esempio: logout (curl)

curl -s -X POST http://localhost:8080/api/auth/logout \
  -H "Authorization: Bearer $TOKEN"

GET /api/auth/session

Verifica se la sessione è valida (passare header `Authorization`).

Esempio: controlla sessione

curl -s -X GET http://localhost:8080/api/auth/session \
  -H "Authorization: Bearer $TOKEN" | jq

2) Transazioni (REST)

Invia transazioni monitorate verso il mercato. Tutte le transazioni REST sono mappate su SAPMonitoredActionReq e devono usare il path basato sul mercato.

POST /api/markets/{market}/transactions

Invio transazione monitored. Il mercato è specificato nel path (`{market}`) quindi il payload NON deve contenere il campo `market`.

{
  "classId": 114809,
  "action": "ADD",
  "smpPayload": {
    "InstrumentId": 12345,
    "Quantity": 1000,
    "Price": 99.5
  }
}

Esempio: invio transazione (curl)

curl -s -X POST http://localhost:8080/api/markets/BV/transactions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"classId":114809,"action":"ADD","smpPayload":{"InstrumentId":12345,"Quantity":1000}}' | jq

Response attesa (200)

{
  "referenceId": null,
  "status": "OK",
  "message": "Transaction accepted"
}

3) Sottoscrizioni (REST)

Creazione e rimozione sottoscrizioni avviene via REST; i dati effettivi arrivano su WebSocket.

POST /api/markets/{market}/subscriptions

Crea una sottoscrizione per il mercato specificato nel path. Il campo `market` NON deve essere incluso nel body.

{
  "username": "trader1",
  "reqId": 0,
  "subscribeType": "All",
  "classId": 100003,
  "classVer": 0,
  "startTs0": 0,
  "startTs1": 0,
  "filterKey": 0,
  "subMask": null
}

Esempio: crea sottoscrizione (curl)

curl -s -X POST http://localhost:8080/api/markets/BV/subscriptions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"username":"trader1","classId":100003,"subscribeType":"All"}' | jq

Response (200)

{ "classId": 100003, "className": "BV_TRADE", "subscriptionKey": 9876 }

GET /api/markets/{market}/subscriptions/user/{username}

Restituisce le sottoscrizioni correnti per l'utente autenticato nel mercato specificato.

Esempio: lista sottoscrizioni

curl -s -X GET http://localhost:8080/api/markets/BV/subscriptions/user/dev \
  -H "Authorization: Bearer $TOKEN" | jq

DELETE /api/markets/{market}/subscriptions/{username}/{classId}

Rimuove la sottoscrizione per l'utente e la classe specificati.

curl -s -X DELETE http://localhost:8080/api/markets/BV/subscriptions/dev/100003 \
  -H "Authorization: Bearer $TOKEN"

4) WebSocket — connessione e ricezione

Usare WebSocket per ricevere eventi push di mercato (quote, trade, book, ecc.). Il WebSocket è autenticato tramite lo stesso token usato per REST.

Endpoint

Path/ws/{market}
Protocolwss (preferibile in produzione) / ws (dev)
AuthQuery param `?token=` o header `Authorization: Bearer <token>`

Comportamento

  • Al momento della connessione il server lega la sessione WebSocket al token e all'username.
  • I messaggi di mercato vengono inviati solo alle sessioni i cui utenti hanno attive sottoscrizioni per il `classId` specifico.
  • I payload sono JSON prodotti da `SMPMessageSerializer` (mapping dinamico da oggetti SMP).

Esempio messaggio ricevuto

{
  "type": "marketData",
  "classId": 100003,
  "className": "BV_TRADE",
  "timestamp": 1670000000000,
  "hashKey": "abc123",
  "data": { "Price": 99.5, "Quantity": 1000 }
}

Conferma di routing (esempio per sviluppatori)

Se sei sottoscritto a `classId=100003` riceverai messaggi come sopra; se non sei sottoscritto il server non invierà nulla per quella classe.

Esempio con WebSocket binary/text framing

I messaggi sono inviati come testo UTF-8 JSON. Non è richiesto framing binario.

5) Sicurezza

TLS / HTTPS / mTLS

In produzione utilizzare HTTPS (server) e TLS per connessioni SDP. Per mTLS impostare i keystore/truststore e la proprietà `SERVER_SSL_CLIENT_AUTH=need`.

JWT

Il server verifica i JWT usando un JWK Set se `JWT_JWK_SET_URI` è configurato; altrimenti in dev viene usato un segreto HMAC di fallback (non sicuro in produzione).

IP Whitelist

È presente un filtro IP opzionale per limitare l'accesso REST ad IP specifici.

6) Esempi rapidi

Login (curl)

curl -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"dev","password":"dev","ipspHost":"127.0.0.1","ipspPort":8800,"useSsl":false}' | jq

Connettersi via WebSocket (wscat)

wscat -c "ws://localhost:8080/ws/BV?token=$TOKEN"
# in produzione usare wss:
wscat -c "wss://localhost:8443/ws/BV?token=$TOKEN" --no-check

Inviare transazione

curl -X POST http://localhost:8080/api/markets/BV/transactions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"classId":114809,"action":"ADD","smpPayload":{"InstrumentId":12345}}'

7) Errori e comportamento

  • 401 Unauthorized — token mancante o non valido.
  • 400 Bad Request — payload non valido (es. campi mancanti o formato errato). Nota: il campo market va passato nel path (`/api/markets/{market}/...`) e non nel body.
  • 500 Internal Server Error — errore lato server (es. class loader non inizializzato, mancanza JAR di mercato).

Esempi di error response

  HTTP/1.1 400 Bad Request
  {
    "error":"BadRequest",
    "message":"Missing required field: market"
  }

  HTTP/1.1 401 Unauthorized
  {
    "error":"Unauthorized",
    "message":"Invalid token"
  }
